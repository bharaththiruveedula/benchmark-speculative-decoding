Speculative decoding
has a crossover point

A controlled A100-vs-L4 benchmark of Qwen2.5-7B, showing that speculative decoding's payoff is a property of the hardware, not just the algorithm.

Abhishek Kumar Scalable Machine Learning — The University of Texas at Austin
August 2026
Motivation02 / 14

The problem

Autoregressive decoding is sequential by construction

  • Every output token requires a full forward pass through the target model — token t+1 cannot start until token t is known.
  • At batch size 1, that pass is memory-bandwidth-bound: the GPU spends more time streaming weights than computing on them.

Does that theory hold on real hardware — and does the answer change with the GPU underneath it?

Background03 / 14

How it works

Draft, then verify

01 · Draft
A small assistant model proposes k tokens autoregressively — cheap, but still sequential on its own.
→
02 · Verify
The target model scores all k draft tokens in a single batched forward pass.
→
03 · Resolve
Accept the matching prefix; resample the first mismatch from the target's own distribution.

Under greedy decoding (do_sample=False), step 3 is deterministic: every accepted or resampled token is exactly what the target model would have produced running alone. Speculative decoding is lossless here — it changes the schedule of computation, not the output.

  • Classical, dynamic, and MTP-proxy share the identical 0.5B assistant — they differ only in the policy deciding how many tokens it drafts per cycle: a fixed 5, an adaptive confidence-gated count, or a fixed 10.
  • Prompt-lookup isn't a smaller version of the same idea — it skips the second model entirely and drafts by matching n-grams already present in the prompt or generated text, which is why its cost profile is fundamentally different.

Why10 / 14

The crossover, explained

A weaker GPU shrinks the relative cost of drafting

A100 → L4, speedup vs. autoregressive (derived from Fig. 08–09)dashed line = autoregressive baseline
  • Running the draft model is a near-fixed cost per step, largely independent of which target GPU it's paired with.
  • On the A100, the target's own verify step is already fast — that fixed draft cost is large relative to it.
  • On the L4, the target's own step costs more — the same fixed draft cost is now a smaller fraction of a bigger total.
  • Prompt-lookup has near-zero marginal cost, so it keeps whatever free tokens it wins — and those tokens are worth more on the slower card.
Scalability & serving implications11 / 14

Beyond one request at a time

This result lives at batch size 1

  • Batching competes with speculation for the same headroom. Production serving pushes toward compute-bound by batching concurrent requests — that amortizes the target's forward pass exactly the way speculative decoding is trying to. The two levers don't stack; they overlap.
  • Cost-per-token, not just tokens/s. L4 costs meaningfully less per GPU-hour than A100. A smaller relative speculative-decoding penalty on cheaper hardware can still net out favorably in $/token even though raw throughput is lower.
  • Design implication: speculative decoding earns its keep in low-batch, latency-sensitive serving (single-user, interactive) — not in high-throughput batched serving, where batching already captures the win speculation is chasing.
Limitations12 / 14

What this benchmark doesn't cover

Read the trend, not the third decimal

  • 4 prompts × 2 repeats per method/GPU — enough to see a consistent, monotonic pattern; not enough for tight confidence intervals.
  • Batch size 1 only; no sweep across concurrent-request batch sizes.
  • Draft length is fixed per method (5 / confidence 0.4 / 10 tokens) and not re-tuned per GPU.
  • One L4 autoregressive run shows a 5.3s warmup outlier vs. ~3.8s steady state, averaged into the reported mean.
  • Greedy decoding only — no sampling-based (temperature > 0) evaluation.
Conclusions13 / 14

Takeaways

Not universal — conditional

  • Speculative decoding's payoff is hardware- and workload-dependent, not universal — on both GPUs tested, every assistant-model method cost throughput rather than saving it.
  • Prompt-lookup decoding is the one method that's a clear, low-risk win on both cards: no draft model, no extra correctness surface, consistent-or-better throughput.
  • Recommendation  don't reach for a draft model by default — measure the crossover on your own target hardware first, or default to lookup-style drafting where the workload has repetitive spans (code, structured text).
Future work14 / 14

What's next

Extending the crossover map

  • Add a T4 (or other sub-24GB) data point — forcing the same 7B/0.5B pair risks tight VRAM headroom, so this needs a deliberate OOM check, not just a config swap.
  • Sweep num_assistant_tokens / confidence threshold per GPU to find each card's optimal draft length, instead of one fixed setting for all hardware.
  • Test batch sizes > 1 to find where speculative decoding's edge, if any, disappears against pure batching.
  • Evaluate sampling-based decoding (temperature > 0), where acceptance becomes probabilistic rather than exact-match.
  • Medusa / EAGLE: public Qwen checkpoints weren't turnkey-compatible with their reference packages — a merged Medusa checkpoint 404s looking for the split medusa_lm_head.pt layout the medusa-llm package expects. A real deployment-packaging gap worth resolving or reporting on its own.
